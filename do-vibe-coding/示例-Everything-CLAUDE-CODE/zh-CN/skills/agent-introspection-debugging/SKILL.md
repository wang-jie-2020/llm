# 代理自省调试

当代理运行反复失败、消耗令牌却没有进展、循环使用相同的工具或偏离预期任务时，请使用此技能。

这是一种工作流程技能，而不是隐藏的运行时技能。它教会代理在升级到人类之前系统地进行自我调试。

## 何时激活

- 最大工具调用/循环限制失败
- 反复重试，没有任何进展
- 上下文增长或提示漂移开始降低输出质量
- 文件系统或环境状态期望与现实不匹配
- 通过诊断和较小的纠正措施可以恢复的工具故障

## 范围边界

激活该技能可以用于：
- 在盲目重试之前捕获失败状态
- 诊断常见的特定于代理的故障模式
- 应用包含的恢复操作
- 生成结构化的人类可读的调试报告

请勿将此技能用作以下目的的主要来源：
- 代码更改后的功能验证；使用“验证循环”
- 当较窄的 ECC 技能已经存在时，进行特定于框架的调试
- 运行时承诺当前线束无法自动强制执行

## 四相循环### 第 1 阶段：故障捕获

在尝试恢复之前，请准确记录故障。

捕获：
- 错误类型、消息和堆栈跟踪（如果可用）
- 最后有意义的工具调用序列
- 代理人试图做什么
- 当前上下文压力：重复的提示、过大的粘贴日志、重复的计划或失控的笔记
- 当前环境假设：cwd、分支、相关服务状态、预期文件

最小捕获模板：```markdown
## Failure Capture
- Session / task:
- Goal in progress:
- Error:
- Last successful step:
- Last failed tool / command:
- Repeated pattern seen:
- Environment assumptions to verify:
```
### 第 2 阶段：根本原因诊断

在更改任何内容之前，将故障与已知模式进行匹配。

|图案|可能的原因 |检查 |
| --- | --- | --- |
|最大工具调用/重复相同命令 |循环或无退出观察者路径 |检查最后 N 个工具调用是否重复 |
|上下文溢出/退化推理 |无边的笔记、重复的计划、超大的日志|检查最近的上下文是否有重复和低信号量 |
| `ECONNREFUSED` / 超时 |服务不可用或端口错误 |验证服务运行状况、URL 和端口假设 |
| `429` / 配额耗尽 |重试风暴或丢失退避|计算重复调用并检查重试间隔 |
|写入/陈旧差异后文件丢失|种族、错误的 CWD 或分支漂移 |重新检查路径、cwd、git 状态和实际文件存在 |
| “修复”后测试仍然失败 |错误的假设|隔离确切的失败测试并重新导出错误 |

诊断问题：
- 这是逻辑失败、状态失败、环境失败还是策略失败？
- 智能体是否失去了真正的目标并开始优化错误的子任务？
- 故障是确定性的还是暂时的？- 验证诊断的最小可逆作用是什么？

### 第三阶段：控制性恢复

通过改变诊断表面的最小动作来恢复。

安全恢复动作：
- 停止重复重试并重申假设
- 修剪低信号背景并仅保留活动目标、阻碍因素和证据
- 重新检查实际的文件系统/分支/进程状态
- 将任务范围缩小到一个失败的命令、一个文件或一项测试
- 从推测推理转向直接观察
- 当故障具有高风险或外部阻塞时，上报给人工处理

请勿声明不受支持的自动修复操作，例如“重置代理状态”或“更新线束配置”，除非您实际上是通过当前环境中的真实工具执行这些操作。

包含的恢复清单：```markdown
## Recovery Action
- Diagnosis chosen:
- Smallest action taken:
- Why this is safe:
- What evidence would prove the fix worked:
```
### 第四阶段：内省报告

以一份报告结束，使下一个代理或人员能够清楚地了解恢复情况。```markdown
## Agent Self-Debug Report
- Session / task:
- Failure:
- Root cause:
- Recovery action:
- Result: success | partial | blocked
- Token / time burn risk:
- Follow-up needed:
- Preventive change to encode later:
```
## 恢复启发法

按顺序选择这些干预措施：

1. 用一句话重申真正的目标。
2.验证世界状态而不是信任内存。
3、缩小失败范围。
4. 运行一项区分检查。
5. 然后重试。

不良模式：
- 用略有不同的措辞重试相同的操作三次

好的模式：
- 捕获失败
- 对模式进行分类
- 运行一项直接检查
- 仅当支票支持时才更改计划

## 与 ECC 集成

- 如果代码发生更改，则在恢复后使用“验证循环”。
- 当失败模式值得转化为本能或以后的技能时，使用“持续学习-v2”。
- 当问题不是技术故障而是决策模糊时，使用“理事会”。
- 如果失败来自冲突的本地状态或存储库漂移，请使用“workspace-surface-audit”。

## 输出标准

当此技能处于活动状态时，不要仅以“我修好了”结束。

始终提供：
- 失败模式
- 根本原因假设
- 恢复动作
- 有证据表明情况现在有所好转或仍然受阻
