# 统一通知操作

当真正的问题不是缺少 ping 时，请使用此技能。真正的问题是分散的通知系统。

这项工作是将分散的事件转化为一个操作员界面：
- 明确的严重性
- 清晰的所有权
- 清晰的路线
- 明确的后续行动

## 何时使用

- 用户想要跨 GitHub、Linear、本地挂钩、桌面警报、聊天或电子邮件的统一通知通道
- CI 故障、审查请求、问题更新和操作员事件到达断开连接的地方
- 当前的设置会产生噪音而不是动作
- 用户希望将重叠的通知分支或积压提案合并到一个 ECC 原生通道中
- 工作区已有挂钩、MCP 或连接工具，但没有一致的通知策略

## 首选表面

从已经存在的开始：
- GitHub 问题、PR、评论、评论和 CI
- 线性问题/项目移动
- 本地挂钩事件和会话生命周期信号
- 桌面通知原语
- 连接的电子邮件/聊天表面（当它们实际存在时）

更喜欢 ECC 原生编排，而不是告诉用户采用单独的通知产品。

## 不可协商的规则- 切勿泄露令牌、秘密、Webhook 秘密或内部标识符
- 分开：
  - 事件源
  - 严重程度
  - 路由通道
  - 操作员动作
- 当中断成本不清楚时默认消化优先
- 不要将每个事件分散到每个通道
- 如果真正的解决方案是更好的问题分类、挂钩策略或项目流程，请明确说明

## 事件管道

将车道视为：

1. **捕捉**事件
2. **分类** 紧迫性和所有者
3. **路由**到正确的通道
4. **崩溃**重复和低信号流失
5. **附加**下一个操作员操作

目标是更少、更好的通知。

## 默认严重性模型

|班级 |示例 |默认处理 |
| --- | --- | --- |
|关键|损坏的默认分支 CI、安全问题、发布受阻、部署失败 |现在打断|
|高|请求审查、公关失败、所有者阻碍移交 |当天提醒 |
|中等|问题状态变化、值得注意的评论、积压工作 |摘要或队列|
|低|重复成功、常规流失、冗余生命周期标记 |压制或折叠|

如果工作区没有严重性模型，请在建议自动化之前构建一个模型。

## 工作流程

### 1.清点当前表面清单：
- 事件源
- 当前频道
- 发出警报的现有挂钩/脚本
- 同一事件的重复路径
- 重要的事情没有浮出水面的无声失败案例

说出 ECC 已经拥有的东西。

### 2. 决定哪些事情值得中断

对于每个事件系列，回答：
- 谁需要知道？
- 他们需要多快知道？
- 这个应该中断、批量还是只是记录？

使用这些默认值：
- 发布、CI、安全和所有者阻止事件中断
- 中等信号更新摘要
- 仅记录遥测和低信号生命周期标记

### 3. 在添加频道之前折叠重复项

寻找：
- GitHub、Linear 和本地日志中出现相同的 PR 事件
- 对于相同的失败重复发出钩子通知
- 应总结评论或状态流失，而不是原始转发
- 相互重复的通道，而不添加更好的操作路径

更喜欢：
- 一份规范总结
- 一位业主
- 一个主要渠道
- 一条后备路径

### 4. 设计 ECC 原生工作流程

对于每个实际的通知需求，定义：
- **来源**
- **门**
- **形状**：立即警报、摘要、队列或仅限仪表板
- **频道**
- **行动**如果 ECC 已经有原语，则首选：
- 操作员分类的技能
- 用于自动发射/执行的钩子
- 委托分类代理
- 仅当缺少真正的桥时才使用 MCP/连接器

### 5.返回一个偏向行动的设计

结束于：
- 保留什么
- 抑制什么
- 合并什么
- ECC接下来应该包裹什么

CURRENT SURFACE
- sources
- channels
- duplicates
- gaps

EVENT MODEL
- critical
- high
- medium
- low

ROUTING PLAN
- source -> channel
- why

CONSOLIDATION
- suppress
- merge
- canonical summaries

NEXT ECC MOVE
- skill / hook / agent / MCP
- exact workflow to build next
```
## 推荐规则

- 比起许多弱车道，更喜欢一条强车道
- 更喜欢中低信号更新的摘要
- 当信号应该自动发出时更喜欢钩子
- 当工作是分类、路由和审查优先决策时，更喜欢操作员技能
- 当根本原因是积压/公关协调而不是警报时，更喜欢“项目流程操作”
- 当用户第一次需要源库存时更喜欢“workspace-surface-audit”
- 如果桌面通知就足够了，就不要发明不必要的外部桥

## 好的用例

- “我们有 GitHub、Linear 和本地挂钩警报，但没有单一操作流程”
- “我们的 CI 失败很吵闹，人们忽略了它们”
- “我想要一项跨 Claude、OpenCode 和 Codex 界面的通知策略”
- “弄清楚什么应该中断而不是进入摘要”
-“将重叠的通知 PR 想法折叠到一个规范的 ECC 通道中”
