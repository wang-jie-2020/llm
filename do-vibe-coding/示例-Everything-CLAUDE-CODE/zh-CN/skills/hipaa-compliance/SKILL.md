# HIPAA 合规性

当任务明确涉及美国医疗保健合规性时，请将此作为 HIPAA 特定的入口点。这项技能有意保持精简和规范：

- “医疗保健-phi-合规性”仍然是 PHI/PII 处理、数据分类、审计日志记录、加密和泄漏预防的主要实施技能。
- 当代码、架构或产品行为需要医疗保健意识的第二遍时，“医疗保健审核者”仍然是专门的审核者。
- “安全审查”仍然适用于一般身份验证、输入处理、机密、API 和部署强化。

## 何时使用

- 请求明确提及 HIPAA、PHI、涵盖的实体、业务伙伴或 BAA
- 构建或审查用于存储、处理、导出或传输 PHI 的美国医疗保健软件
- 评估日志记录、分析、LLM 提示、存储或支持工作流程是否会造成 HIPAA 暴露
- 设计面向患者或面向临床医生的系统，其中最低限度的必要访问和可审核性很重要

## 它是如何工作的

将 HIPAA 视为更广泛的医疗保健隐私技能之上的覆盖：

1. 从“healthcare-phi-compliance”入手，制定具体实施细则。2. 应用 HIPAA 特定决策门：
   - 这是数据 PHI 吗？
   - 该行为者是否是受管辖实体或商业伙伴？
   - 供应商或模型提供商在接触数据之前是否需要 BAA？
   - 访问是否仅限于必要的最低范围？
   - 读/写/导出事件是否可审计？
3. 如果任务影响患者安全、临床工作流程或受监管的生产架构，则升级为“医疗保健审核员”。

## HIPAA 特定护栏

- 切勿将 PHI 放入日志、分析事件、崩溃报告、提示或客户端可见的错误字符串中。
- 切勿在 URL、浏览器存储、屏幕截图或复制的示例有效负载中公开 PHI。
- 需要对 PHI 读写进行身份验证访问、范围授权和审计跟踪。
- 将第三方 SaaS、可观察性、支持工具和 LLM 提供商视为默认阻止，直到 BAA 状态和数据边界明确为止。
- 遵循最小必要访问权限：正确的用户应该只能看到任务所需的最小 PHI 切片。
- 优先选择不透明的内部 ID，而不是姓名、MRN、电话号码、地址或其他标识符。

## 示例

### 示例 1：采用 HIPAA 格式的产品请求

用户请求：> 将人工智能生成的就诊摘要添加到我们的临床医生仪表板中。我们为美国诊所提供服务，需要保持 HIPAA 合规性。

响应模式：

- 激活“hipaa 合规性”
- 使用“healthcare-phi-compliance”来审查 PHI 移动、日志记录、存储和提示边界
- 在发送任何 PHI 之前验证摘要提供商是否受 BAA 覆盖
- 如果摘要影响临床决策，则升级为“医疗保健审核员”

### 示例 2：供应商/工具决策

用户请求：

> 我们可以将支持记录和患者消息发送到我们的分析堆栈中吗？

响应模式：

- 假设这些消息可能包含 PHI
- 除非分析供应商获得 HIPAA 限制工作负载的批准并且数据路径最小化，否则阻止设计
- 如果可能，需要编辑或非 PHI 事件模型
