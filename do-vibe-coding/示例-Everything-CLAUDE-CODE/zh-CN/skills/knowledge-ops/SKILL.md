# 知识运营

管理多层知识系统，用于跨多个商店摄取、组织、同步和检索知识。

更喜欢实时工作空间模型：
- 代码工作存在于真实的克隆存储库中
- 活动执行上下文存在于 GitHub、Linear 和 repo-local 工作上下文文件中
- 更广泛的面向人的笔记可以存在于非回购上下文/存档文件夹中
- 持久的跨机器内存属于知识库，而不是影子存储库工作区

## 何时激活

- 用户想要将信息保存到他们的知识库中
- 将文档、对话或数据提取到结构化存储中
- 跨系统同步知识（本地文件、MCP 内存、Supabase、Git 存储库）
- 删除重复数据或组织现有知识
- 用户说“将其保存到 KB”、“同步知识”、“我对 X 了解多少”、“摄取此内容”、“更新知识库”
- 除了简单的记忆回忆之外的任何知识管理任务

## 知识架构

### 第 1 层：主动执行真相
- **来源：** GitHub 问题、PR、讨论、发行说明、线性问题/项目/文档
- **用于：**工作的当前运行状态- **规则：** 如果某件事影响了正在进行的工程计划、路线图、部署或发布，最好先将其放在这里

### 第 2 层：克劳德代码内存（快速访问）
- **路径：** `~/.claude/projects/*/memory/`
- **格式：** 带有 frontmatter 的 Markdown 文件
- **类型：** 用户偏好、反馈、项目背景、参考
- **用于：** 快速访问在对话中持续存在的上下文
- **在会话开始时自动加载**

### 第 3 层：MCP 内存服务器（结构化知识图）
- **访问：** MCP 内存工具（create_entities、create_relations、add_observations、search_nodes）
- **用于：** 对所有存储的记忆进行语义搜索、关系映射
- **具有可查询图结构的跨会话持久性**

### 第 4 层：知识库存储库/持久文档存储
- **用于：** 策划的持久笔记、会话导出、综合研究、操作员记忆、长格式文档
- **规则：**当内容不是回购拥有的代码时，这是跨机器上下文的首选持久存储

### 第 5 层：外部数据存储（Supabase、PostgreSQL 等）
- **用于：** 结构化数据、大文档存储、全文搜索- **适用于：** 对于内存文件来说文档太大，需要 SQL 查询的数据

### 第 6 层：本地上下文/存档文件夹
- **用于：** 面向人的笔记、存档的游戏计划、本地媒体组织、临时非代码文档
- **规则：** 可写用于信息存储，但不可写为影子代码工作区
- **不要用于：** 应该存在于上游的活动代码更改或存储库事实

## 摄取工作流程

当需要捕获新知识时：

### 1. 分类
它是什么类型的知识？
- 业务决策->内存文件（项目类型）+MCP内存
- 活动路线图/发布/实施状态-> GitHub + Linear优先
- 个人喜好 -> 记忆文件（用户/反馈类型）
- 参考信息->内存文件（参考类型）+MCP内存
- 大文档->外部数据存储+内存中的摘要
- 对话/会话 -> 知识库存储库+内存中的简短摘要

### 2. 重复数据删除
检查这些知识是否已经存在：
- 搜索内存文件中的现有条目
- 使用相关术语查询MCP内存
- 在创建另一个本地笔记之前检查该信息是否已存在于 GitHub 或 Linear 中
- 不要创建重复项。而是更新现有条目。### 3.商店
写入适当的层：
- 始终更新克劳德代码内存以便快速访问
- 使用 MCP 内存进行语义搜索和关系映射
- 当信息更改实时项目真相时，首先更新 GitHub / Linear
- 致力于知识库存储库的持久长格式添加

### 4.索引
更新任何相关索引或摘要文件。

## 同步操作

### 对话同步
定期将对话历史记录同步到知识库中：
- 来源：Claude 会话文件、Codex 会话、其他代理会话
- 目的地：知识库存储库
- 生成会话索引以便快速浏览
- 承诺并推动

### 工作区状态同步
将重要的工作区配置和脚本镜像到知识库：
- 生成目录映射
- 提交前编辑敏感配置
- 跟踪随时间的变化
- 不要将知识库或存档文件夹视为实时代码工作区

### GitHub / 线性同步
当信息影响主动执行时：
- 更新相关的 GitHub 问题、PR、讨论、发行说明或路线图线程
- 当工作需要持久的规划背景时，将支持文档附加到 Linear- 仅在事后镜像本地注释（如果它仍能增加价值）

### 跨源知识同步
将多个来源的知识汇集到一处：
- Claude/ChatGPT/Grok 对话导出
- 浏览器书签
- GitHub 活动事件
- 编写状态摘要、提交和推送

## 记忆模式```
# Short-term: current session context
Use TodoWrite for in-session task tracking

# Medium-term: project memory files
Write to ~/.claude/projects/*/memory/ for cross-session recall

# Long-term: GitHub / Linear / KB
Put active execution truth in GitHub + Linear
Put durable synthesized context in the knowledge base repo

# Semantic layer: MCP knowledge graph
Use mcp__memory__create_entities for permanent structured data
Use mcp__memory__create_relations for relationship mapping
Use mcp__memory__add_observations for new facts about known entities
Use mcp__memory__search_nodes to find existing knowledge
```
## 最佳实践

- 保持内存文件简洁。归档旧数据而不是让文件无限增长。
- 使用 frontmatter (YAML) 作为所有知识文件的元数据。
- 存储前删除重复数据。首先搜索，然后创建或更新。
- 更喜欢每个事实集一个规范的家。避免在本地注释、存储库文件和跟踪器文档中并行复制同一计划。
- 在提交到 Git 之前编辑敏感信息（API 密钥、密码）。
- 对知识文件使用一致的命名约定（小写短横线）。
- 用主题/类别标记条目以便于检索。

## 质量门

在完成任何知识操作之前：
- 没有创建重复的条目
- 从任何 Git 跟踪的文件中编辑敏感数据
- 更新了索引和摘要
- 为数据类型选择适当的存储层
- 在相关位置添加交叉引用
