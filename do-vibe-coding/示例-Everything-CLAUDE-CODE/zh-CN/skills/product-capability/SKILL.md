# 产品能力

这项技能将产品意图转化为明确的工程约束。

当差距不是“我们应该构建什么？”时使用它。但是“在实施开始之前到底必须满足什么条件？”

## 何时使用

- PRD、路线图项目、讨论或创始人说明存在，但实施约束仍然是隐含的
- 某个功能跨越多个服务、存储库或团队，并且在编码之前需要能力合同
- 产品意图很明确，但架构、数据、生命周期或政策影响仍然模糊
- 高级工程师在审查过程中不断重申相同的隐藏假设
- 您需要一个可重复使用的工件，可以在各种安全带和会话中生存

## 规范神器

如果存储库具有持久的产品上下文文件，例如“Product.md”、“docs/product/”或程序规范目录，请在其中更新它。

如果尚不存在功能清单，请使用以下模板创建一个：

- `docs/examples/product-capability-template.md`

目标不是创建另一个计划堆栈。目标是使隐藏的能力约束持久且可重用。

## 不可协商的规则

- 不要发明产品真相。明确标记未解决的问题。- 将用户可见的承诺与实现细节分开。
- 指出什么是固定策略，什么是架构偏好，什么是仍然开放的。
- 如果请求与现有的存储库限制相冲突，请明确说明，而不是进行平滑处理。
- 与分散的临时注释相比，更喜欢一种可重用的功能工件。

## 输入

只阅读需要的内容：

1. 产品意图
   - 问题、讨论、PRD、路线图说明、创始人致辞
2. 当前架构
   - 相关的回购文档、合同、模式、路线、现有工作流程
3. 现有能力背景
   - `PRODUCT.md`、设计文档、RFC、迁移说明、操作模型文档
4. 交货限制
   - 身份验证、计费、合规性、推出、向后兼容性、性能、审查策略

## 核心工作流程

### 1. 重申能力

将询问压缩为一个精确的陈述：

- 用户或操作员是谁
- 这艘船之后存在什么新能力
- 结果会因此而改变

如果这个声明很弱，那么实现就会发生偏差。

### 2.解决能力限制

提取实施前必须满足的约束：

- 业务规则
- 范围边界
- 不变量- 信任边界
- 数据所有权
- 生命周期转换
- 部署/迁移要求
- 失败和恢复期望

这些东西通常只存在于高级工程师的记忆中。

### 3.定义面向实现的合约

制定 SRS 风格的能力计划：

- 能力总结
- 明确的非目标
- 演员和表面
- 所需的状态和转换
- 接口/输入/输出
- 数据模型的影响
- 安全/计费/政策限制
- 可观察性和操作员要求
- 阻碍实施的开放性问题

### 4.转化为执行

以精确的交接结束：

- 准备好直接实施
- 首先需要架构审查
- 首先需要澄清产品

如果有用，请指向下一个 ECC 本机通道：

- `项目流程操作`
- `工作空间表面审计`
- `api-连接器-构建器`
- `仪表板构建器`
- `tdd 工作流程`
- `验证循环`

## 输出格式

按以下顺序返回结果：```text
CAPABILITY
- one-paragraph restatement

CONSTRAINTS
- fixed rules, invariants, and boundaries

IMPLEMENTATION CONTRACT
- actors
- surfaces
- states and transitions
- interface/data implications

NON-GOALS
- what this lane explicitly does not own

OPEN QUESTIONS
- blockers or product decisions still required

HANDOFF
- what should happen next and which ECC lane should take it
```
## 良好的结果

- 产品意图现在足够具体，无需在公关中期重新发现隐藏的约束即可实施。
- 工程审查具有持久的工件，而不是依赖于记忆或 Slack 上下文。
- 生成的计划可在 Claude Code、Codex、Cursor、OpenCode 和 ECC 2.0 规划界面中重复使用。
