# 回购扫描

> 每个生态系统都有自己的依赖管理器，但没有任何工具可以跨 C++、Android、iOS 和 Web 告诉您：有多少代码实际上是您的，哪些是第三方的，哪些是自重的。

## 何时使用

- 接管大型遗留代码库并需要结构概览
- 在重大重构之前——确定什么是核心，什么是重复的，什么是死的
- 审核直接嵌入源代码中的第三方依赖项（未在包管理器中声明）
- 为 monorepo 重组准备架构决策记录

## 分析深度

|水平|文件已读 |使用案例|
|---|---|---|
| `快` |每个模块 1-2 个 |快速盘点庞大目录 |
| `标准` |每个模块 2-5 个 |具有完全依赖性+架构检查的默认审计|
| `深` |每个模块 5-10 个 |添加线程安全、内存管理、API 一致性 |
| `完整` |所有文件 |合并前全面审查|

## 它是如何工作的

1. **对存储库表面进行分类**：枚举文件，然后将每个文件标记为项目代码、嵌入式第三方代码或构建工件。2. **检测嵌入式库**：检查目录名称、标头、许可证文件和版本标记，以识别捆绑的依赖项和可能的版本。
3. **对每个模块进行评分**：按模块或子系统对文件进行分组，然后根据所有权、重复和维护成本分配四个判断之一。
4. **突出结构风险**：指出无用的工件、重复的包装器、过时的供应商代码以及应提取、重建或弃用的模块。
5. **生成报告**：返回简明摘要以及带有每个模块深入分析的交互式 HTML 输出，以便可以异步审查审核。

## 示例

在 50,000 个文件的 C++ monorepo 上：
- 发现 FFmpeg 2.x（2015 年版本）仍在生产中
- 发现相同的 SDK 包装器重复 3 次
- 确定了 636 MB 已提交的 Debug/ipch/obj 构建工件
- 分类：3 MB 项目代码与 596 MB 第三方代码

## 最佳实践

- 从首次审核的“标准”深度开始
- 对包含 100 多个模块的 monorepos 使用“fast”来快速获取库存
- 在标记为重构的模块上增量运行“deep”
- 审查跨模块分析以进行子项目之间的重复检测## 链接
