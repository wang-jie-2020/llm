# 终端操作

当用户想要真正的存储库执行时使用此功能：运行命令、检查 git 状态、调试 CI 或构建、进行缩小修复，并准确报告更改的内容和验证的内容。

这项技能故意比一般编码指导更窄。它是证据优先终端执行的操作员工作流程。

## 技能栈

在相关时将这些 ECC 原生技能引入工作流程：

- “验证循环”用于更改后的精确证明步骤
- 当正确的修复需要回归覆盖时使用“tdd-workflow”
- 当涉及机密、身份验证或外部输入时进行“安全审查”
- `github-ops` 当任务依赖于 CI 运行、PR 状态或发布状态时
- 当需要将经过验证的结果纳入持久的项目背景时，需要进行“知识操作”

## 何时使用

- 用户说“修复”、“调试”、“运行这个”、“检查存储库”或“推送它”
- 任务取决于命令输出、git 状态、测试结果或经过验证的本地修复
- 答案必须区分本地更改、本地验证、提交和推送

## 护栏

- 编辑前检查
- 如果用户仅要求审核/审查，则保持只读- 与临时的临时包装器相比，更喜欢存储库本地脚本和助手
- 在重新运行证明命令之前不要声称已修复
- 除非分支实际向上游移动，否则不要声称已推送

## 工作流程

### 1.解析工作面

解决：

- 确切的回购路径
- 分支机构
- 本地差异状态
- 请求模式：
  - 检查
  - 修复
  - 验证
  - 推

### 2. 首先读取失效表面

在更改任何内容之前：

- 检查错误
- 检查文件或测试
- 检查 git 状态
- 在盲目重新阅读之前使用任何已经提供的日志或上下文

### 3. 缩小修复范围

一次解决一个主要故障：

- 首先使用最小的有用证明命令
- 仅在解决本地故障后升级到更大的构建/测试通过
- 如果命令因相同的签名而持续失败，请停止广泛的重试并缩小范围

### 4. 报告准确的执行状态

使用确切的状态词：

- 检查过
- 本地更改
- 本地验证
- 承诺
- 推
- 被阻止

## 输出格式```text
SURFACE
- repo
- branch
- requested mode

EVIDENCE
- failing command / diff / test

ACTION
- what changed

STATUS
- inspected / changed locally / verified locally / committed / pushed / blocked
```
## 陷阱

- 当可以读取实时存储库状态时，不要从陈旧的内存中工作
- 不要将狭窄的修复范围扩大到回购范围内的流失
- 不要使用破坏性的 git 命令
- 不要忽视不相关的本地工作

## 验证

- 响应命名证明命令或测试
- git相关工作命名repo路径和分支
- 任何推送声明都包括目标分支和确切结果
