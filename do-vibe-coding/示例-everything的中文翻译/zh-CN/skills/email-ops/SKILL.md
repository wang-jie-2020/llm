# 电子邮件操作

当真正的任务是邮箱工作时使用此功能：分类、起草、回复、发送或证明已发送的邮件。

这不是一般的写作技巧。这是围绕实际邮件表面的操作员工作流程。

## 技能栈

在相关时将这些 ECC 原生技能引入工作流程：

- 在起草面向用户的任何内容之前先进行“品牌声音”
- 面向投资者、合作伙伴或赞助商的邮件的“投资者外展”
- 当线程是计费/支持事件而不是一般对应时，为“客户计费操作”
-“知识操作”，当消息或线程之后应该被捕获到持久上下文中时
- 当回复取决于新的外部事实时，称为“研究操作”

## 何时使用

- 用户要求对收件箱进行分类或归档低信号邮件
- 用户想要草稿、回复或新的出站电子邮件
- 用户想知道邮件是否已经发送
- 用户想要证明使用了哪个帐户、线程或发送条目

## 护栏

- 首先草稿，除非用户明确要求实时发送
- 切勿在没有真实发送文件夹或客户端确认的情况下声称已发送消息- 不要随意切换发件人账户；选择与项目和接收者匹配的帐户
- 清理期间不要删除不确定的商业邮件
- 如果任务确实是 DM 或 iMessage 工作，请移交给“messages-ops”

## 工作流程

### 1. 解析精确的曲面

行动前，先解决：

- 哪个邮箱帐户
- 哪个线程或收件人
- 任务是分类、草稿、回复还是发送
- 用户是否想要仅草稿或实时发送

### 2. 撰写前请阅读主题

如果回复：

- 读取现有线程
- 识别最后一次出站触摸
- 确定任何承诺、截止日期或未回答的问题

如果创建新的出站：

- 识别温暖程度
- 选择正确的渠道和发送者帐户
- 在起草之前拉动“品牌声音”

### 3.起草，然后验证

对于仅草稿工作：

- 制作最终副本
- 注明发件人、收件人、主题和目的

对于实时发送工作：

- 首先验证确切的最终主体
- 通过选择的邮件界面发送
- 确认消息已到达已发送或等效的已发送副本存储

### 4. 报告确切状态

使用确切的状态词：

- 起草
- 待批准
- 已发送
- 被阻止
- 等待验证如果发送表面被阻塞，请保留草稿并报告确切的阻塞者，而不是在不说出来的情况下即兴进行第二次传输。

## 输出格式```text
MAIL SURFACE
- account
- thread / recipient
- requested action

DRAFT
- subject
- body

STATUS
- drafted / sent / blocked
- proof of Sent when applicable

NEXT STEP
- send
- follow up
- archive / move
```
## 陷阱

- 在没有发送副本检查的情况下不要声称发送成功
- 不要忽略线程历史记录并编写无上下文的回复
- 不要将邮箱工作与 DM 或短信工作流程混合在一起
- 不要暴露秘密、身份验证详细信息或不必要的消息元数据

## 验证

- 响应命名帐户和线程或收件人
- 任何发送声明包括发送证明或明确的客户端确认
- 最终状态是起草/发送/阻止/等待验证之一
