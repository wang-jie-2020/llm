# 财务计费操作

当用户想要了解资金、定价、退款、团队席位逻辑或产品是否实际按照网站和销售文案暗示的方式运行时，请使用此选项。

这比“客户计费操作”更广泛。该技能用于客户补救。该技能适用于运营商真相：收入状态、定价决策、团队计费和代码支持的计费行为。

## 技能栈

在相关时将这些 ECC 原生技能引入工作流程：

- “客户计费操作”，用于针对特定客户的补救和跟进
- 当竞争对手定价或当前市场证据很重要时进行“研究行动”
- “市场研究”，答案应以定价建议结束
- `github-ops` 当计费真相取决于同级存储库中的代码、待办事项或发布状态时
- 当答案取决于证明结帐、座位处理或权利行为时的“验证循环”

## 何时使用

- 用户询问 Stripe 销售额、退款、MRR 或最近的客户活动
- 用户询问代码中的团队计费、按席位计费或配额堆叠是否真实
- 用户想要竞争对手的定价比较或定价模型基准- 这个问题将收入事实与产品实施事实混合在一起

## 护栏

- 区分实时数据和保存的快照
- 分开：
  - 收入事实
  - 客户影响
  - 代码支持的产品真相
  - 推荐
- 不要说“每个席位”，除非实际的权利路径强制执行它
- 不要假设重复的订阅意味着重复的值

## 工作流程

### 1.从最新的账单证据开始

更喜欢实时计费数据。如果数据不是实时的，请明确说明快照时间戳。

标准化图片：

- 有偿销售
- 活跃订阅
- 结帐失败或不完整
- 退款
- 争议
- 重复订阅

### 2. 将客户事件与产品真相分开

如果问题是特定于客户的，请首先分类：

- 重复结帐
- 真正的团队意图
- 自助服务控制损坏
- 未满足的产品价值
- 付款失败或设置不完整

然后将其与更广泛的产品问题分开：

- 团队计费真的存在吗？
- 座位实际计算在内吗？
- 结帐数量会改变权利吗？
- 该网站是否夸大了当前行为？

### 3. 检查代码支持的计费行为如果答案取决于实现事实，请检查代码路径：

- 结账
- 定价页面
- 权利计算
- 席位或配额处理
- 安装与用户使用逻辑
- 计费门户或自助管理支持

### 4. 以决策和产品差距结束

报告：

- 销售快照
- 问题诊断
- 产品真相
- 建议操作员采取的行动
- 产品或积压订单缺口

## 输出格式```text
SNAPSHOT
- timestamp
- revenue / subscriptions / anomalies

CUSTOMER IMPACT
- who is affected
- what happened

PRODUCT TRUTH
- what the code actually does
- what the website or sales copy claims

DECISION
- refund / preserve / convert / no-op

PRODUCT GAP
- exact follow-up item to build or fix
```
## 陷阱

- 不要将失败的尝试与净收入混为一谈
- 不要仅从营销语言推断团队计费
- 当现有证据可用时，不要凭记忆比较竞争对手的定价
- 不要在没有对问题进行分类的情况下从诊断直接跳转到退款

## 验证

- 答案包括实时数据语句或快照时间戳
- 产品真相声明有代码支持
- 客户影响和更广泛的定价/产品结论清晰分开
