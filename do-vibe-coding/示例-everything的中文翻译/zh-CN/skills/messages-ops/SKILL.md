# 消息操作

当任务是实时消息检索时使用此功能：iMessage、DM、最近的一次性代码或后续操作之前的线程检查。

这不是电子邮件工作。如果主要表面是邮箱，请使用“email-ops”。

## 技能栈

在相关时将这些 ECC 原生技能引入工作流程：

- `email-ops` 当消息任务实际上是邮箱工作时
- 当 DM 线程属于出站网络工作时，`connections-optimizer`
- 当实时线程应告知目标或热路径外展时，“领先情报”
- 当需要将线程内容捕获到持久上下文中时使用“知识操作”

## 何时使用

- 用户说“阅读我的消息”、“检查文本”、“查看私信”或“查找代码”
- 任务取决于实时线程或最近传递到本地消息传递表面的代码
- 用户想要检查哪个源或线程的证据

## 护栏

- 首先解决来源：
  - 本地消息
  - X /社交DM
  - 另一个浏览器控制的消息表面
- 不要在未指明来源的情况下声称已检查线程
- 如果存在已检查的帮助程序或标准路径，则不要即兴进行原始数据库访问
- 如果 auth 或 MFA 阻止表面，请报告确切的阻止者## 工作流程

### 1. 解决确切的线程

在做其他事情之前，先解决：

- 消息面
- 发件人/收件人/服务
- 时间窗口
- 任务是检索、检查还是准备回复

### 2. 起草前阅读

如果任务可能变成外向跟进：

- 读取最新入站信息
- 识别开环
- 如果需要，然后移交给正确的出站技能

### 3. 将代码作为重点检索任务来处理

对于一次性代码：

- 先搜索最近的本地消息窗口
- 尽可能按服务或发件人缩小范围
- 一旦找到代码或集中搜索耗尽就停止

### 4.报告确切的证据

返回：

- 使用的来源
- 线程或发送者（如果可能）
- 时间窗口
- 确切状态：
  - 阅读
  - 代码找到
  - 被阻止
  - 等待回复草稿

## 输出格式```text
SOURCE
- message surface
- sender / thread / service

RESULT
- message summary or code
- time window

STATUS
- read / code-found / blocked / awaiting reply draft
```
## 陷阱

- 不要混淆邮箱工作和 DM/文本工作
- 请勿在未指明来源的情况下声称检索
- 当询问的是最近的代码查找时，不要在广泛的搜索上浪费时间
- 不要在没有暴露拦截器的情况下不断重试被阻止的身份验证路径

## 验证

- 响应命名消息源
- 响应包括发送者、服务、线程或清除阻止程序
- 最终状态是明确且有界的
